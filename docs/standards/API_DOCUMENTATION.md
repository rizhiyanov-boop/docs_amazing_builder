# Стандарт API, интеграций и документации

Этот документ загружается только для задач, связанных с API, интеграциями, project JSON и документацией методов.

## Источники истины

Перед выводами разделять:

- подтверждено исходником;
- выведено из кода, процедуры или схемы;
- предположение;
- вопрос к вендору или бизнесу.

Сверять решение по доступным слоям: бизнес-процесс, публичный контракт, downstream-контракт, фактический код/БД/процедура. Не переносить downstream-бизнес-проверки в публичный API без явного решения.

Конфликт оформлять как finding с severity P1/P2/P3, местом конфликта, риском и требуемой правкой или уточнением.

## Контракт метода

Для orchestration/API отдельно фиксировать:

- внешний endpoint;
- downstream-методы и последовательность вызовов;
- idempotency и retry behavior;
- error mapping;
- response wrapper;
- технические параметры и источник их заполнения.

В каждой строке API-таблицы проверять тип, обязательность, справочник, описание, валидацию, маппинг, маскирование и пример. Пример обязан соответствовать типу и валидации. Персональные данные помечать для маскирования в логах.

Не менять структуру согласованного документа, порядок разделов и названия колонок без явного требования.

## Даты

Для нового публичного контракта интеграционного адаптера использовать доменный формат СНГ:

- дата: DD.MM.YYYY;
- дата и время: DD.MM.YYYY HH:mm:ss.

При вызове downstream преобразовывать дату в формат внешней системы, а ответ — обратно. Не менять уже зафиксированный публичный формат, если это нарушает обратную совместимость; такой случай отмечать отдельно.

## Успешный ответ

Стандартный wrapper: data + techData + warnings.

- data содержит все доменные данные и может быть объектом или массивом;
- techData содержит traceId, spanId, appVersion и appTag;
- warnings содержит предупреждения по необязательным headers либо пустой объект;
- дополнительные корневые result или доменные поля не добавлять.

## Техническое задание

Функциональные требования должны описывать только ожидаемое поведение, быть краткими и однозначными. Не дублировать цель, диаграмму, request/response, маппинги, ошибки и техническое решение. Детали реализации включать только тогда, когда они являются частью ожидаемого поведения.

В таблицах и обычном тексте API-документации не применять моноширное форматирование для полей, типов, значений, форматов и endpoint. Code block использовать только для цельных JSON, XML, cURL и программных примеров.
