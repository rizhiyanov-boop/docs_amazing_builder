# Процесс доработки

## Перед началом

1. Проверить git status.
2. Если дерево не чистое, не смешивать изменения: завершить, закоммитить или согласовать существующую работу.
3. Создать ветку codex/<короткое-название-задачи>, если пользователь не указал иную ветку.
4. Зафиксировать scope, non-goals и acceptance criteria по шаблону docs/TASK_TEMPLATE.md.
5. По docs/CODE_MAP.md открыть только владельцев нужной логики и связанные тесты.

## Во время реализации

- Сначала подтвердить фактическое поведение исходниками и тестами.
- Делать минимальную законченную правку без попутного рефакторинга.
- Не изменять несколько форматов экспорта, если задача относится только к одному.
- Новую чистую логику выносить из App.tsx в профильный модуль.
- Обновлять fixture и документацию только при изменении соответствующего контракта.
- Не оставлять сгенерированные файлы и архивы в Git без явной необходимости.

## Проверка

1. Запустить узкую тестовую группу.
2. Запустить build для TypeScript/runtime-изменений.
3. Для CSS/UI запустить lint:all.
4. Перед релизом или после изменения общего контракта запустить test:ci.
5. Проверить git diff и убедиться, что в коммит не попали секреты и чужие изменения.

## Завершение

В отчете указать измененные области, проверки, известные ограничения и незакрытые риски. Один коммит должен соответствовать одной связной доработке.
